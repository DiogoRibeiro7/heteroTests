\title{heteroTests: A Unified and Reproducible Framework for Heteroscedasticity Diagnostics in R}


\author{by Diogo Ribeiro}

\maketitle

\abstract{%
Heteroscedasticity diagnostics in R are distributed across multiple packages with different interfaces, return objects, assumptions, and workflow conventions. The heteroTests package provides a unified framework for diagnosing non-constant variance in linear-model workflows. It combines classical auxiliary-regression and group-wise procedures with rank-based, ARCH-type, resampling, robust, spatial, and scalable variants behind a consistent interface based on standard htest objects. This article describes the package architecture, validation strategy, batch and streaming workflows, and integration with common R modelling tools. Agreement with established reference implementations is used where available, while simulation studies assess empirical size and power under several variance structures and error distributions. Computational benchmarks evaluate scaling with sample size and illustrate the memory-bounded streaming implementations. Worked examples on simulated and observed data show how heteroTests connects diagnosis, interpretation, and remediation in a reproducible analysis, and how the variance model behind the remediation can itself be tested.
}

\section{Introduction}\label{introduction}

Heteroscedasticity is not a single diagnostic problem. Different procedures
target different alternatives, rely on different assumptions, and are useful
for different data structures. In R, this diversity is reflected in the
software ecosystem: established implementations are distributed across base R
and specialised packages such as \CRANpkg{lmtest} and \CRANpkg{car}
\citep{zeileis2002lmtest, fox2019car}. That distribution is appropriate from a
methodological point of view, but it introduces a practical cost when several
diagnostics must be used in the same analysis. Function signatures differ,
return objects expose different fields, and model or data preparation often has
to be repeated before results can be compared or reported together.

The difficulty is therefore not the absence of individual tests. White's
general test \citep{white1980heteroskedasticity}, the Breusch--Pagan test
\citep{breusch1979simple}, Koenker's studentized variant \citep{koenker1981study}, and
Cook--Weisberg diagnostics \citep{cook1983detection}, among others, are well
established. The software problem is that a reproducible workflow frequently
needs more than one of them, together with a common representation of the model,
the data used for fitting, the diagnostic result, and the choices that determine
how the statistic was computed.

An analyst who needs one of these tests has no reason to change tools:
\texttt{lmtest::bptest()} and \texttt{car::ncvTest()} are single calls, and nothing in this
article argues against them. The difficulty begins with the second test. The
procedures in Table \ref{tab:procedures} that exist outside
\CRANpkg{heteroTests} are spread over 11 packages (Table
\ref{tab:software-comparison}), and no one of those packages has more than
9 of them. Each has its own arguments and its own kind of
result: an \texttt{htest} object from one function, a \texttt{chisqTest} object or an
\texttt{anova} table from another, a bare vector of p-values from a third. Comparing
two tests therefore means installing, learning, and reconciling two packages,
and the work is repeated after the first rejection, when the model has been
adjusted and has to be examined again.

\CRANpkg{heteroTests} addresses this software problem. It provides individual
diagnostic functions, a registry that supports common orchestration, and a
higher-level execution layer that normalises model and data inputs before
running selected procedures. Results returned as \texttt{htest} objects are decorated
with package-specific metadata and a \texttt{hetero\_test} class, while collections are
represented by \texttt{hetero\_test\_suite} or \texttt{hetero\_grouped\_suite} objects. This
keeps compatibility with familiar R hypothesis-test conventions while making
diagnostics easier to combine, tidy, inspect, and pass through automated
workflows.

The package does not propose that a single omnibus procedure should replace
method-specific judgement, and it does not introduce a new test statistic: the
procedures are established ones. Its contribution is the software around them.
The package implements the 29 procedures in Table
\ref{tab:procedures}. Those that need only a model and its data share one
calling convention and one result class, so the set chosen for an analysis
runs in one call and is reported in one table. Around that sit a registry for
extension, grouped-data handling, caching, ecosystem adapters, and
memory-bounded implementations of selected auxiliary-regression tests.

Choosing among the procedures remains the analyst's decision, and the package
supports it with evidence instead of an automatic rule. Table
\ref{tab:procedures} arranges the procedures by the question each one asks
about the variance. The validation study installed with the package runs every
test under a null and an alternative design, and the simulation study in this
article examines four of them in detail, so that statements such as which
tests keep their level under heavy-tailed errors are measured and not assumed.

A second design goal is to avoid making scalability a separate user workflow.
For supported diagnostics, \texttt{runHeteroTests()} estimates the size of the supplied
data and can switch automatically from the ordinary implementation to a
streaming implementation when a configurable memory threshold is exceeded.
The streaming procedures accumulate the cross-products required by the
auxiliary regression rather than materialising its full design matrix. This
preserves the statistic while reducing peak memory use.

A third is to keep the diagnostics meaningful after a model has been adjusted
for heteroscedasticity. Tests applied to a weighted fit are computed on the
weighted scale, where they ask whether the weights are adequate, and the
variance function used to construct feasible weights can be tested as a null
hypothesis in its own right.

The remainder of the article evaluates these design choices rather than
re-deriving the underlying tests. The next section describes the package
architecture and execution model. Later sections validate results against
reference implementations where possible, study empirical size and power under
controlled simulations, benchmark computational scaling, and demonstrate an
end-to-end diagnostic workflow on simulated and on observed data.

\section{Package design}\label{package-design}

The package is organised in four layers: individual statistical procedures,
result normalisation, diagnostic orchestration, and ecosystem integration. This
separation allows a diagnostic to remain independently callable while also
participating in batch workflows.

\subsection{Individual diagnostics and result objects}\label{individual-diagnostics-and-result-objects}

Individual procedures retain explicit names such as \texttt{performWhiteTest()},
\texttt{performBPTest()}, and \texttt{performKoenkerTest()}. The naming convention makes
the diagnostic operation visible while avoiding namespace collisions with
established functions in other packages.

Table \ref{tab:procedures} lists the procedures by the question each one asks
about the error variance, which is also the first thing to settle when
choosing one. A name in code font is the name under which \texttt{runHeteroTests()}
runs the procedure. The others are called directly, most of them because they
need an ordering or grouping variable that a batch call cannot supply.
Szroeter's test needs an ordering too, and under its name it orders the
observations by the fitted values, so its alternative is a variance that rises
with the mean. Streaming versions of the White, Breusch--Pagan, and Koenker
tests are provided in addition, as are diagnostics for the mean function,
collinearity, and influential observations.

Most hypothesis-test functions return standard R \texttt{htest} objects. When a
result is used through the orchestration layer, \CRANpkg{heteroTests} decorates it
with the \texttt{hetero\_test} class and attaches metadata identifying the diagnostic,
the number of observations when available, the fitted model, the data source,
and execution-specific information. The original \texttt{htest} structure is
preserved, so conventional fields such as \texttt{statistic}, \texttt{parameter},
\texttt{p.value}, and \texttt{method} remain available.

The additional class supports a common downstream interface. The package
implements \texttt{tidy()}, \texttt{glance()}, and \texttt{augment()} methods through
\CRANpkg{generics}; suite-level methods combine individual results into data
frames suitable for reporting or subsequent analysis. This design avoids
requiring each underlying diagnostic to expose the same internal computation.

The package also draws what it tests. A family of functions that includes
\texttt{plotResidualsFitted()} and \texttt{plotSpreadLevel()} gives the usual residual
displays for a fitted model, with a weighted fit shown on its weighted scale.
\texttt{plotBeforeAfter()} sets the residuals of a model beside those of its
remedy, and the \texttt{autoplot()} method for a suite draws the evidence of each test
against a chosen level. All of them return \CRANpkg{ggplot2} objects, which can
be modified or combined like any other. The last two are used in the worked
examples below.

\subsection{Registry-based orchestration}\label{registry-based-orchestration}

The diagnostic registry maps character names to functions that accept a model
and data and return a diagnostic result. Built-in entries include the classical
auxiliary-regression tests together with resampling, rank-based,
high-dimensional, and spatial procedures. Users can extend the registry with
\texttt{registerDiagnostic()}, after which custom diagnostics can be selected by
\texttt{runHeteroTests()} in the same way as built-in entries, and
\texttt{listDiagnostics()} returns the names registered.

This registry is deliberately simpler than a plugin framework. It provides a
stable dispatch point without requiring a new object hierarchy for every
method. The registry is also shared with the broader diagnostic machinery in
the package, which means that adding a compatible function is sufficient for it
to participate in batch execution.

The default call

\begin{verbatim}
fit <- lm(mpg ~ wt + qsec, data = mtcars)

runHeteroTests(fit, mtcars)
\end{verbatim}

runs White and Breusch--Pagan diagnostics. Additional registered procedures are
selected explicitly:

\begin{verbatim}
runHeteroTests(
  fit,
  mtcars,
  tests = c("white", "breusch_pagan", "koenker", "wild_bootstrap")
)
\end{verbatim}

The four names in this call are examples. Any name shown in code font in Table
\ref{tab:procedures} can be requested in the same way.

A small default set is intentional. Running many diagnostics automatically would
blur the distinction between exploratory screening and a test chosen because
its assumptions and alternative hypothesis are appropriate for the model.

\subsection{Input normalisation and grouped analyses}\label{input-normalisation-and-grouped-analyses}

The public execution layer accepts fitted \texttt{lm} and \texttt{glm} objects, formulas,
selected \CRANpkg{tidymodels} workflow or parsnip objects, and compatible
data-frame representations. Internally, these inputs are normalised before a
diagnostic is dispatched. Formula inputs are fitted using the supplied data,
while supported workflow and parsnip objects are reduced to their underlying
engine fits.

Grouped tibbles receive different treatment. When a formula-based specification
can be recovered, the model is refitted independently within each group and the
result is returned as a \texttt{hetero\_grouped\_suite}, together with the group keys.
The package therefore treats grouping as a set of separate modelling problems,
rather than applying one global residual vector to pre-partitioned data.

The input layer also accepts \texttt{data.table} and \texttt{dtplyr}-backed data, and
\texttt{runSurveyHeteroTests()} takes the data out of a survey design object. That
function does not use the sampling weights, strata, or clusters of the design:
its results are those of the unweighted diagnostics. These adapters are not
intended to redefine the statistical meaning of the underlying diagnostics;
they reduce
the amount of conversion code required before a supported model can enter the
same diagnostic pipeline.

\subsection{Caching and failure handling}\label{caching-and-failure-handling}

Repeated diagnostic calls can reuse cached results. \texttt{runHeteroTests()} builds
an analysis key from the model, data, selected tests, and relevant execution
parameters when caching is enabled and the optional hashing dependency is
available. Cached objects are returned using the same suite classes as newly
computed results.

Errors are analysed at the orchestration layer rather than being silently
discarded. The package records diagnostic context, can attempt a supported
fallback, and produces structured failure results for grouped analyses where
continuing with the remaining groups is preferable to aborting the entire
operation. For ordinary ungrouped calls, unrecoverable errors are still raised
to the caller.

\subsection{Memory-bounded auxiliary regressions}\label{memory-bounded-auxiliary-regressions}

White, Breusch--Pagan, and Koenker diagnostics also have streaming
implementations. Their common computational problem is an auxiliary regression
whose statistic depends on its coefficient of determination. Rather than
constructing the complete auxiliary design matrix, the streaming code processes
observations in chunks and accumulates

\[
  X^\top X, \qquad X^\top y, \qquad
  \sum_i y_i, \qquad \text{and} \qquad \sum_i y_i^2.
\]

These quantities are sufficient to solve the auxiliary least-squares problem
and recover the residual and total sums of squares. If
\(\widehat{\beta}=(X^\top X)^{-1}X^\top y\), the residual sum of squares can
be written as

\[
  \mathrm{SSE}=y^\top y-\widehat{\beta}^\top X^\top y,
\]

while the total sum of squares is obtained from the accumulated first and
second moments of the response. The resulting \(R^2\) is therefore computed
without retaining all rows of the auxiliary design simultaneously.

This matters most for White's test, where squares and cross-products can expand
the auxiliary design substantially. The implementation also checks for
rank-deficient accumulated systems and can omit interaction expansion when the
number of regressors exceeds a configurable limit. If \CRANpkg{Matrix} is
available, sufficiently large chunk cross-products may be evaluated using sparse
matrices.

\texttt{runHeteroTests()} estimates the size of the supplied data and uses these
streaming implementations automatically for supported diagnostics when the
configured threshold is exceeded. The threshold and chunk size remain user
controls, so the same API can be used for both ordinary in-memory and
memory-constrained analyses.

\subsection{Weighted fits and variance functions}\label{weighted-fits-and-variance-functions}

Two design decisions concern models that have already been adjusted for
heteroscedasticity. The first is what a diagnostic should compute for a fit
obtained with \texttt{lm(...,\ weights\ =\ w)}. Such a fit asserts that the error
variance is proportional to \(1/w_i\), so its raw residuals are
heteroscedastic by assumption and a statistic computed from them cannot show
whether the weights are adequate. For weighted fits the diagnostics therefore
use the Pearson residuals, the raw residuals multiplied by the square roots of
their weights. These are the residuals of the equivalent unweighted regression
and have constant variance when the weights are correct, so the null
hypothesis becomes that the weights are adequate. Variance regressors,
grouping variables, and ordering variables remain on their original scale.
The resampling tests regenerate the response and refit the mean model, and
for a weighted fit they do so in that equivalent regression: they draw from the
Pearson residuals, return each draw to the scale of its observation by
dividing it by the square root of its weight, and refit with the weights. The
quantile-regression slope test fits its quantile regressions without the
weights, and for a weighted fit it stops with an error instead of testing a
different model.

The second decision is to make the variance model used for remediation
explicit and testable. \texttt{fitWLS()} estimates a variance function from the OLS
residuals and refits by feasible weighted least squares. Its \texttt{var\_formula}
argument names the variance regressors, and \texttt{form} selects an exponential
function, in which the log variance is linear in those regressors
\citep{harvey1976estimating}, or a power function, in which it is linear in their
logarithms \citep{park1966estimation}. The fitted function is stored with the
returned model.

\texttt{performVarianceFormTest()} takes such a function as its null hypothesis. The
other diagnostics test constant variance, so a rejection shows that the
variance changes with some variables but not whether a particular functional
form describes the change. The variance-function test regresses the squared
standardised residuals of the weighted fit on the variance regressors and on
additional terms, by default the squares and cross-products of those
regressors, and reports the \(F\) test of the additional terms. It is a
regression-based specification test
\citep{wooldridge1990unified, wooldridge1991application}. Retaining the variance
regressors in the auxiliary regression removes the first-order effect of
having estimated the variance function from the same residuals.

\section{Validation strategy}\label{validation-strategy}

The validation strategy is organised around the claim being checked rather than
around the package function that happens to implement it. Three forms of
evidence are used: agreement with an established implementation, independent
reconstruction of a published statistic, and behavioural tests of statistical
or computational properties.

\subsection{Agreement with established implementations}\label{agreement-with-established-implementations}

Where another R implementation exposes the same statistic under the same
assumptions, the package test suite compares both the statistic and the
associated p-value. This is the strongest validation available for wrappers of
well-established methods because it checks not only formula transcription but
also practical details such as degrees of freedom, alternative hypotheses, and
centering conventions.

The current suite includes direct comparisons with \CRANpkg{lmtest} for the
classical Breusch--Pagan, studentized Breusch--Pagan/Koenker, and
Goldfeld--Quandt tests \citep{goldfeld1965tests, zeileis2002lmtest}. Mean-centred Levene,
median-centred Brown--Forsythe, and Cook--Weisberg/non-constant-variance
diagnostics are checked against \CRANpkg{car} \citep{fox2019car}. Group-wise
variance procedures are also compared with base R implementations for Bartlett
and Fligner--Killeen tests and, where available, with \CRANpkg{vartest} for
Hartley and O'Brien procedures.

Weighted fits show why the choice of reference matters. For a model fitted
with weights, \texttt{car::ncvTest()} computes its score statistic from Pearson
residuals, whereas \texttt{lmtest::bptest()} retains the raw residuals and weights
the auxiliary regression. The two functions therefore test different
hypotheses, and only the first asks whether the weights are adequate.
\CRANpkg{heteroTests} follows the Pearson-residual convention described
earlier. On weighted fits its score test is compared with \CRANpkg{car}, and
its Goldfeld--Quandt test with \texttt{lmtest::gqtest()} applied to the equivalent
transformed regression.

These comparisons use explicit numerical tolerances in the automated test
suite. The tolerance depends on the implementation pair: some functions match
to floating-point equality, while others are checked within a small numerical
tolerance because the two implementations may differ in intermediate linear
algebra without changing the intended statistic.

\subsection{Independent reconstruction}\label{independent-reconstruction}

An external package is not always available, and using another implementation
is not sufficient when both could share the same mistake. For this reason, a
second group of tests reconstructs the claimed statistic directly from its
published definition or from lower-level base-R operations.

Examples include the Cook--Weisberg score statistic \citep{cook1983detection},
Harvey's LM statistic for multiplicative variance \citep{harvey1976estimating},
Szroeter's ordered-variance statistic, Engle's ARCH LM statistic
\citep{engle1982autoregressive}, and the McLeod--Li procedure \citep{mcleod1983diagnosis}, which is checked
against a Ljung--Box calculation on squared residuals. The same approach is
used for O'Brien's transformed observations and for degrees-of-freedom
behaviour under rank-deficient auxiliary models.

This layer is particularly useful for implementation details that are easy to
get subtly wrong. Examples caught during package development include scaling of
ordered-variance statistics, auxiliary-model degrees of freedom, and the
construction of resampling null distributions.

\subsection{Behavioural and invariant checks}\label{behavioural-and-invariant-checks}

Some properties are better validated as invariants than by comparing a single
number. Property-based tests verify that supported diagnostics return valid
\texttt{htest} objects with finite statistics and p-values in \([0,1]\) over randomly
generated inputs. Simulation-based regression tests check that selected
classical procedures have empirical Type-I error close to the nominal level,
using a tolerance based on the Monte Carlo standard error rather than a fixed
arbitrary margin.

The same principle covers weighted fits. When heteroscedastic data are fitted
with the correct weights, a diagnostic should reject at its nominal rate. This
property has to be tested by simulation, because no comparison on unweighted
fits can reveal it: before version 0.12.0 the heteroscedasticity diagnostics
read the raw residuals of a weighted fit, agreed with their references on
every unweighted comparison, and rejected a correctly weighted model in every
replication of the package's validation design. In the current version
32 procedures reject between
2\% and
8\% of such models at the 5\% level
in that design, based on 400 replications each.
The resampling tests, measured in a design of their own, reject between
5.0\% and
5.3\%, based on
2,000 replications each.

Resampling procedures receive separate checks because an apparently plausible
implementation can still produce invalid p-values. Bootstrap and permutation
p-values use the finite-simulation convention

\[
  p = \frac{1 + \#\{T_b \ge T_{\mathrm{obs}}\}}
           {B_{\mathrm{eff}} + 1},
\]

which prevents an estimated p-value of exactly zero and accounts for failed
replicates through the effective number of simulations. Null-imposed residual
resampling is also checked for leverage correction and, for a weighted fit,
against resampling in the equivalent unweighted regression, while unsupported
model classes and transformed responses are rejected rather than silently
refitted under a different statistical model.

Finally, the streaming implementations are compared directly with their
ordinary in-memory counterparts. For White, Breusch--Pagan, and Koenker tests,
the test suite checks equality of the statistic and p-value within numerical
tolerance for identical data. This verifies the principal claim of the
streaming layer: reduced peak memory use should not define a different
diagnostic.

\subsection{Reproducibility of the evidence}\label{reproducibility-of-the-evidence}

The article does not hard-code validation numbers. Reference comparisons and
behavioural checks live in the package test suite, while the empirical size,
power, and performance results reported later are read at render time from
recorded runs, each identified by package version, environment, and seed. This
separation is intentional. Unit and reference tests answer whether an
implementation is computing the intended object; simulation and benchmark
sections answer how those procedures behave under selected data-generating
processes and computational loads.

The distinction also limits the claims made here. Agreement with another
implementation is evidence of computational equivalence for the cases tested,
not proof that the underlying statistical procedure is appropriate for every
analysis. Likewise, satisfactory empirical size under a simulation design does
not establish finite-sample validity outside that design. The purpose of this
validation framework is therefore narrower: to make the software behaviour
auditable and to reduce the risk that integration work changes the statistic a
diagnostic is supposed to compute.

\section{Simulation study}\label{simulation-study}

The simulation study separates calibration under the null from power under
specific alternatives. This distinction is important because a procedure that
rejects frequently under a heteroscedastic alternative is not useful if it also
substantially exceeds its nominal rejection probability under homoscedasticity.

All experiments use the linear mean model

\[
  y_i = 1 + 2x_i + \sigma(x_i)\varepsilon_i,
  \qquad x_i \sim U(0,1),
\]

with independent errors. The significance level is \(\alpha=0.05\). Within
each Monte Carlo replication the same simulated data set is supplied to all
diagnostics, so differences in rejection rates are not inflated by using
different random samples for different tests.

The design is deliberately minimal. With a single regressor, each variance
pattern is a function of one variable and can be written down exactly. A
regressor that is uniform on the unit interval produces no high-leverage
observations, so differences between the tests are not driven by a few points.
The intercept and slope are immaterial: all four statistics are computed from
least-squares residuals, which do not depend on the regression coefficients.

The study includes White, classical Breusch--Pagan, Koenker, and a two-sided
Goldfeld--Quandt test ordered by \(x\). These procedures represent different
ways of detecting variance structure: general auxiliary-regression expansion,
linear score-type alternatives, a studentized variant less dependent on
normality, and an ordered two-sample variance comparison.

\subsection{Empirical size}\label{empirical-size}

Empirical size is estimated under \(\sigma(x)=1\) for sample sizes
\(n\in\{50,100,250\}\). The smallest is one at which the asymptotic
reference distributions of these tests are in doubt, the largest one at which
they should be adequate if they are going to be, and the middle value shows
how quickly they improve. Two error distributions are considered: Gaussian
errors and Student \(t_5\) errors rescaled to unit variance. The heavier-tailed
case is included because agreement with a reference implementation does not
imply that an asymptotic approximation is well calibrated under non-normal
finite samples.

For each reported rejection rate \(\widehat p\), the simulation records the
Monte Carlo standard error

\[
  \operatorname{MCSE}(\widehat p)
  = \sqrt{\frac{\widehat p(1-\widehat p)}{B_{\mathrm{eff}}}},
\]

where \(B_{\mathrm{eff}}\) is the number of valid replications. An
approximate 95\% Monte Carlo interval is
\(\widehat p \pm 1.96\operatorname{MCSE}(\widehat p)\), truncated to
\([0,1]\). Such an interval quantifies simulation uncertainty; it is not a
confidence interval for a population parameter estimated from observed data.

\subsection{Power alternatives}\label{power-alternatives}

Power is studied under three patterns for the error standard deviation, with
Gaussian errors:

\begin{itemize}
\tightlist
\item
  \textbf{linear:} \(\sigma(x)\propto 0.5+x\), which increases monotonically with
  \(x\);
\item
  \textbf{step:} \(\sigma(x)\propto 0.5\) for \(x<0.5\) and \(1.5\) otherwise, an
  abrupt change at the midpoint;
\item
  \textbf{U-shaped:} \(\sigma(x)\propto 0.35+2(x-0.5)^2\), smallest at the centre
  of the covariate range and increasing toward both extremes.
\end{itemize}

The three were chosen to differ in kind, not in size. In the first two the
standard deviation triples across the range of \(x\), once gradually and once
at a single point; in the third it is about two and a half times larger at the
ends than in the middle, with no overall trend.

For each pattern, an effect-strength parameter
\(\gamma\in\{0.25,0.50,0.75,1.00\}\) interpolates between constant
variance, which would be \(\gamma=0\), and the full pattern at
\(\gamma=1\). The four equally spaced values trace the power curve between
the two; the results reported below are for \(\gamma=1\). The resulting
standard-deviation vector is
renormalised to unit root-mean-square scale. Consequently, increasing
\(\gamma\) changes the \emph{shape} of heteroscedasticity without simply changing
the overall noise magnitude. This avoids the common error of calling a global
multiplicative scale change an increase in heteroscedastic effect size.

The non-monotone U-shaped alternative is included deliberately. A test ordered
by a single covariate direction can be powerful against monotone changes while
having much less sensitivity to variance patterns that increase at both ends of
the covariate range. The purpose of the study is therefore comparative rather
than to identify a universally dominant diagnostic.

\subsection{Reproducible experiment}\label{reproducible-experiment}

The complete experiment is implemented in
\texttt{paper/scripts/simulation\_study.R}. The manuscript run uses the seed 20261007,
which is set once at the start of the script, and writes both results and
simulation metadata to \texttt{paper/generated/}:

\begin{verbatim}
system2(
  "Rscript",
  c("paper/scripts/simulation_study.R", "2000")
)
\end{verbatim}

The default manuscript configuration uses 2,000 replications per design cell.
With a rejection probability near 0.05 this corresponds to a Monte Carlo
standard error of approximately 0.005, which is small enough to distinguish
material size distortions from ordinary simulation noise without pretending
that the estimated rejection rates are exact.

Numerical results and figures are intentionally read from committed extracts of
the successful workflow artifact rather than copied from earlier drafts. The
full experiment used \texttt{heteroTests} 0.11.2 under R 4.6.1 on Ubuntu 24.04.5;
the workflow and artifact identifiers are recorded in the file
\texttt{PROVENANCE.md} under \texttt{paper/generated/}. Version 0.12.0, which the rest of
the article
describes, changes these four procedures only for weighted fits. The study
fits unweighted models, and a rerun of the full experiment under 0.12.0

\section{Computational performance}\label{computational-performance}

The performance study is designed around two separate questions. The first is
the cost of the package's validation and integration layer relative to
established reference implementations. The second is whether the streaming
implementations provide a useful memory--time trade-off while preserving the
underlying statistic. Combining these questions into one benchmark would be
misleading because the reference packages and the streaming code solve
different software problems.

\subsection{Reference-package overhead}\label{reference-package-overhead}

For statistically equivalent procedures, \CRANpkg{heteroTests} is benchmarked
against the corresponding implementation in \CRANpkg{lmtest} or
\CRANpkg{car}. The benchmark covers classical Breusch--Pagan, Koenker's
studentized form, and the Cook--Weisberg/non-constant-variance score test.

Synthetic regression data are generated with four predictors and several
variance patterns. Sample size increases from small inputs to \(10^5\)
observations in the manuscript configuration. For each test and sample size we
record elapsed time and, when the \CRANpkg{bench} package is available,
allocated memory. The benchmark also records absolute differences in the
reported statistic and p-value relative to the reference implementation.

Raw wall-clock ratios are interpreted cautiously. At small sample sizes both
implementations may complete near the timer's resolution, so a ratio can become
unstable or infinite even when the absolute difference is negligible. The
article therefore reports absolute timings and statistical agreement rather
than presenting a single cross-package ``speed-up'' number.

\subsection{Exact versus streaming implementations}\label{exact-versus-streaming-implementations}

White, Breusch--Pagan, and Koenker tests are benchmarked separately using their
ordinary and streaming implementations on the same generated datasets. The
streaming variants process fixed-size chunks and accumulate the cross-products
described earlier, while the exact variants follow the ordinary in-memory path.

For every benchmark cell, the experiment records

\begin{itemize}
\tightlist
\item
  elapsed time;
\item
  allocated memory when available;
\item
  the absolute difference in the test statistic; and
\item
  the absolute difference in the p-value.
\end{itemize}

The statistic and p-value differences are the primary correctness checks. A
streaming implementation is only useful if reduced memory requirements do not
change the diagnostic being computed. Runtime is a secondary trade-off: chunked
processing may be slower for data that already fit comfortably in memory.

\subsection{Reproducible benchmark workflow}\label{reproducible-benchmark-workflow}

The complete benchmark is implemented in \texttt{paper/scripts/performance\_study.R}; summary
tables and figures are generated by \texttt{paper/scripts/summarise\_performance.R}. Both
scripts write to \texttt{paper/generated/}, together with metadata describing seeds,
sample sizes, replication counts, chunk size, and whether memory profiling was
available.

\begin{verbatim}
system2("Rscript", "paper/scripts/performance_study.R")
system2("Rscript", "paper/scripts/summarise_performance.R")
\end{verbatim}

The manuscript does not use the retired \texttt{scaling\_plot.pdf} as evidence. The
reported performance results were generated from \texttt{heteroTests} 0.11.2 under
R 4.6.1 on Ubuntu 24.04.5 and are preserved with workflow provenance. They
were not regenerated for version 0.12.0, whose changes to the benchmarked
procedures are confined to the handling of weighted fits.

\subsection{Performance results}\label{performance-results}

The reference comparisons show that integration and validation have a measurable
runtime cost, but do not change the reported inference. Across all benchmarked
sample sizes, the largest median p-value difference from the corresponding
\CRANpkg{lmtest} or \CRANpkg{car} implementation is
2.9e-12.
At \(n=10^5\), median elapsed times for \CRANpkg{heteroTests} are
0.272 s
for Breusch--Pagan,
0.291 s
for Koenker, and
0.097 s
for NCV. The corresponding reference timings are retained in the generated
benchmark table rather than collapsed into a single speed ratio.

The streaming comparison gives a more direct software result (Figure
\ref{fig:streaming-memory}). At
\(n=250{,}000\), measured allocation falls from
198.0 MB
to
102.3 MB
for Breusch--Pagan, from
251.8 MB
to
102.3 MB
for Koenker, and from
333.4 MB
to
214.8 MB
for White. In this benchmark the chunked implementations are also faster, though
that should be treated as an empirical result of this design rather than a
guarantee.

Most importantly, the largest absolute statistic difference between exact and
streaming computations at \(n=250{,}000\) is
3.39e-11,
and the largest p-value difference is
5.21e-12.
The benchmark therefore supports the intended interpretation of streaming as a
different computational path to essentially the same statistic, not as an
approximate test.

\section{A reproducible diagnostic workflow}\label{a-reproducible-diagnostic-workflow}

The previous sections treat diagnostics as statistical and computational
objects. This section shows how the package is intended to be used in an
analysis: diagnose a specific model, interpret the evidence, choose a
follow-up whose assumptions match the variance pattern, and check the variance
model that the follow-up relies on.

A controlled example is useful here because the correct mean and variance
structures are known. We generate

\[
  y_i = 1 + 2x_i + \varepsilon_i,
  \qquad
  \varepsilon_i \sim N\!\left(0, \exp(1.8x_i)\right),
\]

with \(x_i\sim U(-1,1)\). The mean model is therefore correctly specified as
linear, while the log variance is linear in the same predictor. This is a case
where feasible weighted least squares is an interpretable follow-up rather than
a generic attempt to make a diagnostic p-value disappear. The same steps are
then applied to observed data, where the answer is not known in advance.

\begin{verbatim}
set.seed(20261008)

n_workflow <- 500L
workflow_data <- data.frame(
  x = stats::runif(n_workflow, -1, 1)
)
workflow_data$sigma <- exp(0.9 * workflow_data$x)
workflow_data$y <- 1 + 2 * workflow_data$x +
  stats::rnorm(n_workflow, sd = workflow_data$sigma)

ols_fit <- stats::lm(y ~ x, data = workflow_data)
\end{verbatim}

\subsection{Diagnose the fitted model}\label{diagnose-the-fitted-model}

The example uses three regression-based diagnostics with complementary
properties: White's general test, classical Breusch--Pagan, and Koenker's
studentized form. They are selected explicitly rather than by running every
available diagnostic, and Table \ref{tab:workflow-diagnostics} reports them.

estimation, a transformation, or a different mean specification.

\subsection{Model the variance}\label{model-the-variance}

Here the data-generating mechanism makes a variance model appropriate. The
\texttt{fitWLS()} helper estimates a feasible-GLS model by regressing logged squared
OLS residuals on the original design matrix, exponentiating the fitted
log-variance, and using its inverse as the weight. It does not invert individual
squared residuals. This is the default, exponential variance function; the
\texttt{var\_formula} and \texttt{form} arguments select other variance regressors or a power
function. Table \ref{tab:workflow-wls} sets the coefficients of the two fits
side by side.

\begin{verbatim}

Because the mean model is unchanged, the point of WLS is not to force the raw

\(\widehat\sigma_i^2\), the relevant residual scale is

\[
  r_i^{(w)} =
  \frac{y_i-\widehat y_i}{\widehat\sigma_i}
  =
  \sqrt{w_i}\,(y_i-\widehat y_i).
\]

A useful before/after check therefore compares the OLS residuals with these
weighted residuals, not the raw residuals from the weighted fit.
\texttt{plotBeforeAfter()} draws that comparison, using the weighted residuals for a
weighted fit (Figure \ref{fig:workflow-weighted-residuals}).

weights as known, whereas \texttt{fitWLS()} estimated them from the same residuals.
In the validation study installed with the package, with a correctly specified
variance function and Gaussian errors, the Koenker test applied to a
\texttt{fitWLS()} fit rejected

of the time at the 5\% level with 150 observations and

of the time. Harvey's test, which repeats the regression the weights were

0\%
of the time with 600 observations.

hypothesis is the variance function that produced the weights, and in the same
validation designs it rejected
5\%
of the time with 150 observations and
5\%
with 600. Applied to \texttt{wls\_fit}, it tests the fitted exponential function
against the square of the variance regressor. Two further calls test a
deliberately incomplete variance function, which contains only a quadratic
term, first against its default added term and then against the linear term it
omits.

  var_formula = ~ I(x^2)
)

  against = ~ x
)
\end{verbatim}

Table \ref{tab:workflow-variance-form-table} reports the three tests. The
first row is the function \texttt{fitWLS()} fitted. The test finds no evidence
against it, and the estimated slope of the log variance is
1.68
against a true value of 1.8. The other two rows show what such a result does
and does not establish. The quadratic-only function omits the linear
dependence that generated the data, yet it is not rejected when tested against
its default added term, because the misfit does not lie in that direction.
Tested against the omitted linear term, it is rejected decisively. The test has power against the terms it is given; a
non-rejection is evidence that those terms are not needed, not that the
functional form is correct.

A different inferential goal would lead to a different follow-up. If the
coefficient estimates were the primary target and no variance model were
scientifically justified, heteroscedasticity-consistent covariance estimation
would be a natural alternative \citep{zeileis2006sandwich}. Conversely, evidence of
mean-model misspecification should be addressed before treating the variance
alone. The diagnostic layer is therefore a decision point in the modelling
workflow, not an instruction to apply WLS after every rejected null.

\begin{verbatim}
cats_wls <- fitWLS(cats_fit)

  cats_log_fit,
  cats,
  tests = c("white", "breusch_pagan", "koenker"),
  use_cache = FALSE,
  progress = FALSE
)
\end{verbatim}

The first keeps the model and changes the weights. The exponential variance
function fitted by \texttt{fitWLS()} is not rejected
(\(F=1.52\), \(p=0.22\)), and neither is a power function
(\(F=1.36\), \(p=0.25\)). Body weights in these data run from
2 to 3.9 kg, and over that range the two functions
are too close for 144 observations to separate, which is the
limitation of the variance-function test noted above. The weighted fit moves
the slope from 4.03 to
3.86 grams per kilogram.

The second remedy changes the model. On the logarithmic scale the slope is
1.01, so heart weight is close to
proportional to body weight, and none of the three tests rejects (p-values
between 0.52 and
0.57). Which of the two descriptions to prefer
is not a question the diagnostics answer. It depends on whether the analysis
needs the relationship on the original scale or accepts an error that is
proportional to the response.

\subsection{Established diagnostic implementations}\label{established-diagnostic-implementations}

Base R already provides high-quality procedures for several classical
equal-variance problems, including Bartlett and Fligner--Killeen tests.
\CRANpkg{heteroTests} does not improve these statistics by reimplementing them;
the value of including compatible procedures is that their results can
participate in the same reporting and orchestration layer as
regression-specific diagnostics.

\CRANpkg{lmtest} provides established regression diagnostic procedures,
including Breusch--Pagan and Goldfeld--Quandt tests
\citep{zeileis2002lmtest}. These implementations are used as numerical reference
points in the validation suite. When an analyst needs only one such procedure,
calling \texttt{lmtest::bptest()} or \texttt{lmtest::gqtest()} directly is simpler than
introducing another abstraction layer.

\CRANpkg{car} has a broader regression-diagnostics role and provides, among
other tools, the non-constant-variance score test and Levene-type variance
comparisons \citep{fox2019car}. These functions also serve as reference
implementations in the package tests. The relationship is therefore
complementary: \CRANpkg{car} supplies mature specialised diagnostics, while
\CRANpkg{heteroTests} supplies a common execution and result layer when these
kinds of diagnostics must be combined with others.

\CRANpkg{vartest} concentrates on tests for equality of variances. The
\CRANpkg{heteroTests} validation suite compares its Hartley and O'Brien
implementations against \CRANpkg{vartest} where that package is available. For an
analysis centred specifically on group-variance testing, the specialised
package remains a natural direct interface.

\CRANpkg{skedastic} is the closest in scope. It is devoted to
heteroskedasticity in the linear regression model and collects 25 tests,
several of which \CRANpkg{heteroTests} does not implement, together with
auxiliary variance models, feasible weighted least squares, and
heteroskedasticity-consistent covariance estimators. All of its tests are
tests for a single linear regression model. The group-wise, time-series, and
spatial procedures of Table \ref{tab:procedures} lie outside it, which is why
an analysis that needs both still crosses a package boundary.

The package also has a form of one of these tests for which we found no other
R implementation. The test of \citet{glejser1969new} regresses the absolute
residuals on a variance regressor, and its statistic has its nominal level
when positive and negative errors are equally likely, and in general not
otherwise \citep{godfrey1996some}. \citet{im2000robustifying} and \citet{machado2000glejser} gave
a correction that removes the condition. \texttt{skedastic::glejser()} uses the
absolute residuals as they are, and so does \texttt{performGlejserTest()} unless it
is called with \texttt{robust\ =\ TRUE}, which applies the correction. The validation
study installed with the package runs both forms of the package's test on
skewed errors of constant variance, with 50 to
1000 observations. At the 5\% level the uncorrected form rejects
between 8.8\% and
17.7\% of the time, and the corrected one
between 4.6\% and
5.9\%.

The test of \citet{harrison1979test} is a case where the implementations agree on the
statistic and differ in the p-value. The statistic is the share of the
residual sum of squares that falls in the first part of the sample, ordered by
a chosen variable, and under normal errors its null distribution depends on
the regressors. \texttt{lmtest::hmctest()} simulates the p-value from a regression on
a constant alone, whatever the model, and \texttt{skedastic::harrison\_mccabe()}
applies Imhof's formula \citep{imhof1961computing} after keeping one copy of each
repeated eigenvalue. \texttt{performHarrisonMcCabeTest()} applies the formula to all
of them, so its p-value is exact for normal errors given the regressors. In
the validation study installed with the package it rejects a true null
hypothesis between 4.3\% and
5.3\% of the time at the 5\% level
under Gaussian errors, with 40 to 400 observations, with
and without weights. Under Student \(t_5\) errors it rejects between
11.7\% and
16.3\% of the time, and the
Goldfeld--Quandt and Szroeter tests between
9.6\% and
15.8\% on the same
samples.

The remaining packages in Table \ref{tab:software-comparison} each contribute
one or two procedures as part of a wider purpose: \CRANpkg{whitestrap} for
White's test and its bootstrap, \CRANpkg{heplots} for Box's M,
\CRANpkg{FinTS} and \CRANpkg{TSA} for ARCH effects in time series,
\CRANpkg{spdep} for spatial autocorrelation, and \CRANpkg{quantreg} for
quantile regression. None of this is a defect of those packages. It is the
reason that running, comparing, and reporting a set of tests chosen from
different rows of Table \ref{tab:procedures} otherwise takes bridging code.

\subsection{Detection and robust inference are different tasks}\label{detection-and-robust-inference-are-different-tasks}

\CRANpkg{sandwich} addresses a different problem. Its
heteroscedasticity-consistent covariance estimators modify coefficient
inference without requiring the analyst to specify a parametric variance model
\citep{zeileis2006sandwich}. A diagnostic package and a robust-covariance package
therefore answer different questions: one provides evidence about the
constant-variance assumption, while the other provides an inferential strategy
that can remain valid when that assumption is relaxed.

This distinction matters in practice. The worked example used feasible WLS
because the variance structure was deliberately modelled. If the coefficient
estimates were the primary target and no scientifically defensible variance
model were available, a \CRANpkg{sandwich} covariance estimator could be a more
appropriate follow-up. \CRANpkg{heteroTests} should therefore be viewed as
complementary to robust covariance estimation rather than as a substitute for
it.

\subsection{What the integration layer adds}\label{what-the-integration-layer-adds}

The software contribution of \CRANpkg{heteroTests} appears when an analysis
requires several diagnostics or must be embedded in a larger reproducible
workflow. In that setting the package adds five pieces of infrastructure that
are not properties of any individual heteroscedasticity test:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Common result semantics.} Hypothesis-test outputs retain the familiar
  \texttt{htest} structure and can be decorated as \texttt{hetero\_test} objects with
  diagnostic and execution metadata.
\item
  \textbf{Registry-based orchestration.} \texttt{runHeteroTests()} selects registered
  diagnostics by name, supports user-defined entries, and returns suite objects
  with a common downstream interface.
\item
  \textbf{Input adapters.} Supported formulas, fitted models, grouped tibbles,
  \texttt{data.table}/dtplyr objects, survey designs, and selected tidymodels objects
  enter the same preprocessing path.
\item
  \textbf{Reproducibility and validation.} Reference comparisons, behavioural tests,
  explicit failure handling, and common metadata reduce the amount of bridging
  code needed when several diagnostics are reported together.
\item
  \textbf{Alternative computational paths.} Selected auxiliary-regression tests can
  switch to memory-bounded streaming implementations without changing the
  public diagnostic interface.
\end{enumerate}

These conveniences have a cost. The performance study shows measurable
overhead relative to a direct call to a narrowly focused reference function,
particularly for Breusch--Pagan and Koenker diagnostics. That overhead reflects
input validation, result decoration, and the surrounding orchestration layer;
it should not be presented as evidence that the statistical procedure itself
is computationally superior.

The practical boundary is therefore straightforward. For a single established
test, the specialised implementation is often the shortest and clearest
choice. \CRANpkg{heteroTests} becomes useful when the analysis needs multiple
diagnostic families, consistent result handling, extensible orchestration,
large-data execution paths, or a reproducible bridge from diagnosis to
subsequent modelling decisions.

\section{Discussion}\label{discussion}

The results in this article reinforce a point that is easy to lose when many
diagnostics are available behind one interface: heteroscedasticity testing is
not a model-selection tournament. Different procedures are sensitive to
different departures from constant variance, and their finite-sample behaviour
depends on assumptions that are not erased by software unification.

The simulation study illustrates this directly. Under Gaussian homoscedastic
errors, the four procedures considered remain close to the nominal 5\% level,
but their behaviour separates under heavier tails. Classical Breusch--Pagan and
Goldfeld--Quandt tests become substantially oversized under standardized
\(t_5\) errors, whereas Koenker and White remain much closer to nominal size.
The distinction between classical and studentized score tests is therefore not
an implementation detail. It affects the practical meaning of the result when
normality is questionable.

Power is equally alternative-specific. Monotone linear and step changes are
detected readily by several procedures in the simulation, while the symmetric
U-shaped alternative strongly favours White's more general auxiliary expansion.
This does not establish White as uniformly preferable; it shows why a test
chosen for an ordered or monotone variance alternative can have little power
when the actual variance structure is non-monotone. A useful workflow therefore
starts from a plausible variance mechanism, which is how Table
\ref{tab:procedures} is organised, not from the desire to run the largest
possible collection of tests.

That point also limits how \texttt{runHeteroTests()} should be interpreted. The
function is an orchestration mechanism, not a multiple-testing procedure.
Running many correlated diagnostics and then reporting the smallest p-value
would alter the error rate and is not justified by the package interface. Batch
execution is most useful when a small set of procedures has been selected for
different but scientifically defensible alternatives, or when the exercise is
explicitly exploratory and reported as such.

\subsection{Statistical scope of the software adapters}\label{statistical-scope-of-the-software-adapters}

The input-normalisation layer broadens software compatibility, not statistical
validity. Accepting a \texttt{glm}, a survey design, grouped data, or a tidymodels
object does not imply that every registered diagnostic is theoretically valid
for every such model. Each procedure retains the assumptions of its underlying
statistical definition. The adapters reduce conversion and bookkeeping code;
they do not convert a linear-model diagnostic into a general theorem for other
model classes.

The same distinction applies to grouped execution. Refitting a formula within
each group produces a reproducible set of separate diagnostics, but inference
across those groups still raises the ordinary issues of multiplicity,
dependence, and unequal sample size. The suite object records and organises the
results; it does not solve those inferential problems automatically.

\subsection{Computational trade-offs}\label{computational-trade-offs}

The streaming implementation reduces peak allocation by replacing the full
auxiliary design with accumulated cross-products. The benchmark shows that this
can materially reduce measured memory use while preserving the reported
statistic to numerical precision in the designs studied. However, this
computational route is not free of trade-offs.

The calculation works with \(X^\top X\), whose condition number is the square of
the condition number of \(X\). Ill-conditioned auxiliary designs can therefore
be more numerically delicate than a decomposition applied directly to the full
design matrix. The implementation checks for rank deficiency and falls back to
more stable solves where possible, but the streaming path should still be
interpreted as a memory-oriented algorithm, not as a universally superior
linear-algebra method.

White's test introduces an additional dimensionality issue because squares and
cross-products expand the auxiliary design as the predictor count increases.
The implementation limits interaction expansion beyond a configurable number of
regressors. That safeguard prevents uncontrolled growth in memory and
computation; it changes the auxiliary specification and should therefore be
treated as an explicit computational choice rather than as an exact substitute
for the unrestricted White expansion.

The performance comparison with \CRANpkg{lmtest} and \CRANpkg{car} also
shows the cost of abstraction. Input checking, result decoration, and
orchestration add runtime relative to direct calls for some diagnostics. At the
same time, the numerical agreement results indicate that the additional
software layer is not changing the intended inference in the reference cases
tested. The relevant trade-off is therefore convenience and reproducibility
against modest overhead, not statistical quality against speed.

\subsection{Remediation is a modelling decision}\label{remediation-is-a-modelling-decision}

Detecting non-constant variance does not determine the next model. The worked
example uses feasible WLS because the simulated variance is log-linear in the
model design, matching the variance model estimated by \texttt{fitWLS()}. In an
observational analysis, that structure would need scientific or empirical
justification. \texttt{performVarianceFormTest()} supplies part of the empirical
side by testing a fitted variance function against added terms, but it cannot
confirm a functional form, and variance functions that are close over the
observed range of the regressors will all be accepted. Diagnostics of
constant variance applied to a \texttt{fitWLS()} fit remain informative for
comparison with the original model; they are not calibrated tests, because
they treat estimated weights as known.

Other goals lead to different responses. Heteroscedasticity-consistent
covariance estimation can preserve the original coefficient estimates while
changing their estimated uncertainty. A transformation changes the target model
itself. Explicit generalized least squares models the variance structure.
Misspecification of the conditional mean should be addressed before attributing
all residual pattern to the variance. The package exposes several follow-up
helpers, but none removes the analyst's responsibility to decide which
inferential problem is actually being solved.

\subsection{Limits of the empirical evidence}\label{limits-of-the-empirical-evidence}

The simulation study covers one linear mean model, three variance patterns,
three sample sizes, two null error distributions, and four diagnostics. Its
findings describe those designs; they are not an exhaustive power ranking. In
particular, panel, spatial, clustered, high-dimensional, and time-series
settings require separate evaluation. The rejection rates quoted for weighted
fits and for the variance-function test come from the package's own validation
study, which uses a different design, and are not part of that comparison. The
example on observed data is a single data set: it illustrates the workflow and
is not evidence about the tests.

The performance study is likewise platform-specific. The reported timings and
allocations come from one R version and one Linux Actions environment, with a
fixed predictor dimension and benchmark configuration. Absolute runtime should
not be interpreted as a hardware-independent property of the package. The more
portable findings are the observed numerical agreement with reference
implementations and the relative reduction in allocation between exact and
streaming paths on the same platform.

Finally, the package's breadth creates a maintenance obligation. A unified
interface is useful only if the individual procedures remain tied to their
published definitions and reference implementations. The validation matrix,
simulation tests, and explicit provenance used in this article are therefore
part of the software contribution rather than auxiliary documentation.

\section{Conclusion}\label{conclusion}

\CRANpkg{heteroTests} provides a common software layer for heteroscedasticity
diagnostics in R. Its contribution is not a new omnibus test and not a claim
that one diagnostic should replace established specialised implementations.
Instead, the package standardises execution and result handling, supports
extensible batch workflows, records diagnostic context, validates selected
implementations against independent references, and supplies memory-bounded
paths for large auxiliary regressions. It also follows an analysis past the
first rejection: diagnostics of a weighted fit are computed on the weighted
scale, and the variance function behind the weights can itself be tested.

The empirical results support that narrower claim. Reference comparisons agree
to numerical precision for the procedures evaluated. The simulation study
shows why method choice still matters: classical Breusch--Pagan and
Goldfeld--Quandt tests are sensitive to heavy-tailed null errors in the studied
design, while White's broader auxiliary specification is much more sensitive to
a non-monotone U-shaped variance alternative. The performance study shows that
streaming White, Breusch--Pagan, and Koenker calculations can reduce measured
allocation substantially while reproducing the in-memory statistics to
numerical precision on the benchmark platform.

The practical value is therefore reproducibility of the \emph{workflow} rather than
automatic selection of the \emph{method}. Analysts can combine several justified
variance diagnostics without writing bespoke bridging code, preserve the
information needed to reconstruct what was computed, and choose a follow-up
model or covariance strategy based on the scientific purpose of the analysis.
